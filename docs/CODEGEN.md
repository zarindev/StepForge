# Code export

_By Md Zarin Tasnim · part of the StepForge documentation_

**Exports** (left rail) turns scenarios into a ready-to-run project or a test document. Pick the application,
environment, which tests (all, a module, a tag or chosen scenarios) and a target, then **Preview** every generated
file or **Download** a zip. From the Test Explorer, the `</>` button on a scenario opens Exports with that scenario
chosen. Earlier downloads are listed under *Earlier exports* and can be downloaded again. The CLI does the same:
`stepforge codegen --app <slug> --target <id> --out <dir>` (see [CLI.md](CLI.md)).

## Targets

| Target | Id | What you get |
|---|---|---|
| **Playwright Test** (TypeScript) | `playwright-ts` | `playwright.config.ts`, one spec per scenario, page objects (optional), helpers for API, DB, email |
| Playwright + pytest (Python) | `playwright-py` | pytest-playwright tests, `conftest.py`, page objects (optional) |
| **Cypress** (JavaScript) | `cypress-js` | `cypress.config.js`, Testing Library queries, Node tasks for DB and email, page objects (optional) |
| **Selenium + pytest** (Python) | `selenium-py` | Chrome tests through a small `Browser` helper, page objects (optional) |
| Selenium + JUnit 5 (Java) | `selenium-java` | Maven project, one class per scenario, REST Assured for API steps, page objects (optional) |
| pytest + requests | `pytest-requests` | API scenarios only |
| REST Assured + JUnit 5 (Java) | `rest-assured` | API scenarios only, Maven project |
| k6 script | `k6` | API scenarios as k6 groups with checks (1 VU, 1 iteration; fails when a check fails) |
| Postman collection v2.1 | `postman` | Folders per module and scenario, tests per assertion, captured values as variables |
| cURL commands | `curl` | `requests.sh` (bash, curl 7.87+, jq) with status and JSON checks |
| Test cases (Markdown) | `docs-markdown` | One document: steps in plain English, test-case tables |
| Gherkin features | `docs-gherkin` | One `.feature` per module; test cases become Scenario Outline examples |
| Test cases (Excel) | `docs-xlsx` | One row per test case, with a status column to fill in |

Code projects include a README (setup, run, configuration, warnings), `.env.example`, `.gitignore`, the SQL of each
database step under `sql/`, and optionally **GitHub Actions** and **GitLab CI** files. Every generated file says
*Generated by StepForge — by Md Zarin Tasnim*; documents also say *Prepared by …* (Settings → Reports).

## How steps are translated

- **Locators:** the first (best-ranked) locator of each step. Playwright uses `getByTestId/Role/Label/Placeholder/Text`;
  Cypress uses Testing Library's `findBy*` queries (same meaning); Selenium uses a small finder
  (`find.js`) that matches test ids, ARIA roles with accessible names, labels, placeholders and text the way StepForge
  does, and waits like Playwright. StepForge's self-healing (falling back to other locators) is not exported.
- **Values:** `{{env.baseUrl}}` and `{{env.x}}` become configuration with the exported environment's values as
  defaults (`BASE_URL`, `X`); `{{secret.x}}` becomes the environment variable `X` with **no value** — StepForge never
  puts secret values in exports (the generator never even receives them); `{{data.x}}` reads the test case;
  `{{vars.x}}` is a local variable set by earlier steps (`captureAs`); `{{random.*}}` and *Generate data* use Faker /
  Datafaker with the same kinds.
- **Test cases** become parameterised tests (Playwright loop, `pytest.mark.parametrize`, JUnit `@ParameterizedTest`,
  Cypress `forEach`, k6 data loop, Gherkin Examples).
- **Checks** keep StepForge's meaning: the same operators (`equals` with "200" = 200, `contains`, `matches`,
  `inRange`, `noNulls`…) and targets (`status`, `time`, `header:x`, JSONPath, `rowCount`, `value`, `rows[0].x`,
  `column:x`) are implemented in a small helper shipped with each project.
- **Reusable blocks and called scenarios** are inlined (with a comment). Conditions and loops become `if`/`for`;
  formats without control flow (Postman, cURL) write loops over a fixed list out once per item.
- **Database steps** use `DB_<CONNECTION>_URL` (`postgres://…`, `mysql://…`, `sqlite:path`) with pg / mysql2 /
  better-sqlite3 (JS), psycopg / PyMySQL / sqlite3 (Python) or JDBC (Java). Placeholders are converted for each
  driver.
- **Email steps** read a Mailpit server (`MAILPIT_URL`): wait for an email, check it, extract a one-time code, a link
  or a regular expression, open a link.
- **Page Object Model** (optional): one class per page, one getter/constant per element. Pages are taken from the
  last opened URL or the last URL check ("URL matches `/$`" → `HomePage`); elements after a tab switch or inside an
  iframe stay inline.

**Never silently broken:** a step a target cannot express exactly becomes a `TODO(StepForge): …` comment and is listed
in the export dialog, the README (*Needs attention*) and the CLI output. Examples: visual checkpoints, Lighthouse and
load tests in functional suites, MongoDB and data-quality steps, IMAP inboxes, OAuth2 auth, JSON Schema checks,
multi-tab / iframes / drag and drop in Cypress, JavaScript *Run script* steps in Python and Java, browser steps in
API-only targets.

## Verified

`npm run verify:export` starts CareClinic and Mailpit, imports the suite in
`demo/clinic-app/stepforge/codegen-suite.json` (UI registration through a reusable block, an API + SQLite scenario, a
loop and a condition, a sign-up with an emailed one-time code) into a throwaway StepForge, exports it, installs the
exported project's own dependencies and runs it. CI runs it for Playwright (`exported-code` job);
`npm run verify:export -- --targets all [--pom]` runs every target whose tools are installed and reports the others
as skipped.

Run on 2026-10-07 on macOS 26.5 (Apple silicon), with and without page objects, all against CareClinic:

| Target | Tools | Result |
|---|---|---|
| Playwright Test | Node 23, @playwright/test 1.63.0, Chromium | 4/4 passed |
| Cypress | Cypress 15.21.1, @testing-library/cypress 10 | 4/4 passed |
| Playwright + pytest | Python 3.13.1, pytest 9.1.1, playwright 1.63.0 | 4/4 passed |
| Selenium + pytest | selenium 4.50.0, Chrome 154 | 4/4 passed |
| Selenium + JUnit 5 | Temurin 17.0.20, Maven 3.9.9, Selenium 4.27.0, REST Assured 5.5.0 | 4/4 passed |
| pytest + requests | requests 2.34.2 | 2/2 passed (API scenarios) |
| REST Assured | as above | 2/2 passed (API scenarios) |
| k6 | k6 v2.2.0 | 17/17 checks |
| cURL | bash, curl 8.7.1, jq 1.7.1 | all checks passed |
| Postman | newman 6.2.2 | 17/17 assertions |

Each was also run with a wrong password: the tests that sign in fail (and only those), so passing results are not
vacuous. The documents (Markdown, Gherkin, Excel) were opened and read back. Unit tests snapshot every target with a
fixture that uses every step type and check that all generated TypeScript/JavaScript parses, all Python compiles,
the shell script passes `bash -n`, JSON parses, and that a secret value never appears.

Not verified: the generated GitHub Actions / GitLab CI files themselves (no runners were used), Windows, and the
`exported-code` CI job on GitHub (this repository has no remote yet).
